「马上用上」具体是哪几步

公开仓库提供源码模块与可直接运行的试玩 App（1 个主端 + 2 个从端模拟器）。接入路径：
  1. Gradle 引入 qingzhu-company-sdk（它以 api 方式传递 qingzhu-core 与两个示例协议）；
  2. 声明蓝牙 / 定位权限，Android 12+ 动态申请 BLUETOOTH_SCAN、BLUETOOTH_CONNECT；
  3. init → startScan → createTask → task.send(...)，四步就能发第一条指令；
  4. 要接自家设备：实现一个 ProtocolPlugin 注册进去，内核与业务代码都不用改。

和常见做法比，差在哪

常见做法 / 薄封装 SDK青竹 BLE SDK

多台同时建连，Android BLE 栈互相撞车（133 / 排队 / 越连越慢）建连串行闸门 + 1–7 并发容量，按机型体检给起点

02 / 给 SDK 使用者

从初始化到每个场景，几行代码就够

心智模型只有一句：万物皆任务。任务 = 一台设备 + 一条可选命令；内核负责寻人、排队、连接、发送、失败重试与收尾。以下示例均对应仓库中的公开 API。

接入准备

settings.gradle / build.gradle
// settings.gradle：引入源码模块
include ':qingzhu-core', ':qingzhu-company-sdk',
        ':qingzhu-protocol-generic', ':qingzhu-protocol-eddystone'

// app/build.gradle：只需依赖门面，内核与协议由它传递暴露
dependencies { implementation project(':qingzhu-company-sdk') }

// AndroidManifest.xml（Android 12+ 还需动态申请）
BLUETOOTH_SCAN · BLUETOOTH_CONNECT · ACCESS_FINE_LOCATION · WAKE_LOCK

五步发第一条指令

1

初始化

幂等；注入内核并注册两个开源示例协议。要换成自家协议，注册自己的插件即可。

Java
QingzhuSdk.init(context.getApplicationContext());
2

扫描（按 stableId 去重，每秒批量回调）

扫描常开；任务需要寻人时内核会自动拉起。退出界面或登出时由业务调用 stopScan()。

Java
QingzhuSdk.startScan(devices -> showList(devices));
QingzhuSdk.setScanStateListener(scanning -> updateIndicator(scanning));
// 需要过滤时：startScan(ScanOptions.builder()...build(), listener)
3

建任务 / 取任务

createTask 会替换该设备已有任务；多页面共享用 getTask 复用，避免误删后来者。

Java
QTask task = QingzhuSdk.createTask(mac);
task.setConnectParams(Collections.singletonMap("activeKey", key));  // 连接参数属于任务
4

表达意图并发送

一条 QCommand 说清「这次干什么」；连、发、断、重试由任务池跑完。回调在主线程，每条命令恰好一次。

Java
QCommand cmd = QCommand.builder()
        .send("{\"action\":\"echo\"}")
        .disconnectAfter()          // 短连接：发完自动断
        .build();
task.send(cmd, result -> {
    if (result.isSuccess()) showOk(result.payload());
    else showError(result.stage(), result.code(), result.error());
});
5

观察任务 / 清理

注册后立即推一次快照；任务自带状态、进度、已发字节、错误。页面销毁时按 mac 清理，订阅随 owner 自动取消。

Java
Subscription sub = QingzhuSdk.observeAll(owner,
        snapshots -> render(snapshots));   // 不可变快照列表

QingzhuSdk.deleteTask(mac);             // 取消 + 断开 + 移出任务池

场景速查：点一下看写法

同一个 QCommand.builder()，加减几个方法就是不同命令；连接参数单独放在任务上。

结果模型：失败也说清楚卡在哪

TaskState：UNKNOWN · READY · SEARCHING · QUEUED · CONNECTING · CONNECTED · SENDING TaskStage：SEARCH · CONNECT · SEND · TIMEOUT · CANCEL · DELETE · BUSY · CLOSED TaskOutcome：SUCCEEDED · CONNECT_FAILED · OPERATION_FAILED · CANCELLED ErrorCode：1102 超时 · 1201 协议未注册 · 1301~1306 扫描类
为什么简洁：以前要在 Activity 里维护连接状态、定时器、重试计数、分包队列和一堆回调分支；现在业务只写「给谁、发什么」，状态、顺序、资源由任务池唯一拥有。快速反复进出页面时，新任务替换旧任务、旧意图作废，也不会出现旧页面迟到的 onDestroy 把新连接断掉。
03 / 给 SDK 开发者

接入自家设备协议，只写一个插件

内核只认识 ProtocolPlugin 这一种「协议形状」。把自家设备的识别方式、连接准备、收发格式告诉内核，扫描、连接、调度、重试、错误模型全部复用，不需要改内核或门面。

插件要实现什么

能力必需作用
protocolType() / recognizer()必需协议唯一 id 与广播识别器；扫描按注册顺序问协议，第一个认领者解析
identityKey()建议声明身份字段，stableId 由内核统一分配，换 MAC 仍认得同一台
beforeConnect()可选连接前钩子：重寻址、取密钥、握手；完成后调 onReady
onGattReady()可选业务准备：找特征、协商 MTU、使能通知、认证
connectSteps()可选自定义连接步骤；返回 null 走内核默认流程
heartbeatCommand() / heartbeatConfig()可选声明心跳指令与协议级节奏；返回 null 即零开销不做心跳
scanConfig() / scanManufacturerIds()可选系统扫描参数与硬件过滤下沉；全部协议都声明厂商 ID 时才下沉
install()建议装配钩子：把自己的 ActionHandler 注册进路由
configurableParams()可选只声明可配项，不赋值；取值权留给上层 SDK

对接流程

  1. 写 Recognizer：从广播里认出自家设备，并解析出身份 metadata；
  2. 写 ActionHandler：把业务 JSON + 字节附件翻译成设备帧，解析应答并返回 JsonResponse；
  3. 按设备需要补 beforeConnect / onGattReady（认证、MTU、通知）；
  4. 实现 ProtocolPlugin，在 install() 里注册 Handler；
  5. 初始化后 QingzhuSdk.registerProtocol(new MyProtocolPlugin())；
  6. 用 QingzhuSdk.getProtocols() 确认注册成功，即可用统一的 task.send(json) 发指令。
Java · 注册自己的协议
QingzhuSdk.init(context);
QingzhuSdk.registerProtocol(new MyProtocolPlugin());  // 幂等，不改内核

// 业务代码始终不变：JSON 进、JSON 出，协议差异关在插件里
QTask task = QingzhuSdk.createTask(mac);
task.send(QCommand.builder().send("{\"action\":\"setConfig\"}").build(), r -> handle(r));

路由与失败语义

JSON → JSON

内核不解析业务 JSON

发送链路经 TaskScheduler 按 mac 串行进入 ActionRouter，按 protocolId 找到对应 ActionHandler；结果统一以 JsonResponse 返回。core 不认识业务语义，也不预设消息格式。

明确的失败

不会静默成功

已连上但 Handler 未注册，返回 PROTOCOL_NOT_FOUND = 1201；整个协议插件不在包里，则广播无人认领，最终以 30s 寻人超时失败。两种都带 stage / error，可直接定位。

仓库内已有两个可直接参考的实现：GenericProtocolPlugin（Service Data 0xFFE0，echo / OTA / 心跳）与 EddystoneProtocolPlugin（0xFEAA UID / URL / TLM）。

04 / 给架构研究者

总体架构与底层机制

这一节只讲设计，不贴实现代码。核心前提一句话：BLE 资源在一个进程里是共享的，必须有明确的所有者；否则任何调度策略都无法生效。

总体分层

门面层QingzhuSdk / QSdk
唯一对外入口，直接暴露内核类型（QDevice / QTask / QCommand）；负责初始化、协议装配、扫描订阅、任务创建与调度旋钮。不做白标包装。
↓
内核层QTaskPool · ConnectionPool · ScanEngine · TaskScheduler
协议无关的状态与资源所有者：任务池管「一台设备一个任务 + 意图队列」，连接池管「同时连几台 + 建连闸门」，扫描引擎管「识别 → 去重 → 缓存」，调度器保证同一 mac 串行。
↓
平台层BleAdapter · AndroidBleAdapter · AndroidBleScanner · AndroidGattClient
把内核语义翻译成 Android 能力。平台接口只约定「扫描 / 连接 / 发数据」三件事；唯一触碰 BluetoothGatt 的地方在平台实现里，便于替换与测试。
↓
协议插件层ProtocolPlugin · ProtocolRegistry · ActionRouter
设备差异上浮到插件：识别广播、连接前握手、MTU/通知、心跳、业务帧翻译。内核按 protocolId 路由，新增设备不改内核。

六个核心机制

01 任务池

一设备一任务

任务 = 设备 + 可选命令；命令进有界 FIFO 意图队列，状态在 UNKNOWN / READY 与 SEARCHING → QUEUED → CONNECTING → CONNECTED → SENDING 之间流转。所有终态收口到一处，保证每条命令恰好回调一次。

02 连接池

串行进门，池化管理

并发容量 1–7，建连走全局串行闸门，避免 Android BLE 栈同时建连互相撞车；连上之后各任务并行推进。容量起点按机型体检给出，支持手动接管。

03 身份与缓存

stableId 全链路去重

协议声明身份字段，扫描引擎生成稳定 id；扫描缓存按它组织、跨换址只留最新地址。连接前以「地址新鲜度」为唯一闸门，换址自动跟随，不重复建任务。

04 扫描引擎

识别、去重、自愈

逐条识别并实时更新缓存，按秒批量上报；看门狗应对零广播、启动限流避开系统风控，蓝牙开关与亮屏事件自动恢复扫描，离开范围只置灰不删快照。

05 超时与重试

分层，不互相打架

连接回调兜底、连接流程步骤超时、单条命令应答超时、大块传输停滞检测各管一层；优先级为单条命令 > 连接级参数 > 全局配置 > 默认值。失败带 stage / error，重试间隔与退避统一。

06 生命周期治理

迟到回调与资源回收

取消、断开、删除三种语义严格区分；删除任务会作废排队意图、递增发送代次让迟到回调失效，并回收仍占用的链路。心跳探活与永久重连复用同一套收尾流程。

关键设计取舍

取舍为什么这样设计
连接参数属于任务，不属于命令「这台设备怎么连」是设备级信息；命令只描述「这次干什么」。core 只承载、不翻译，由协议在连接前钩子读取。
扫描常开，不因建连暂停扫描缓存要求逐条实时更新，连接池的重连轮询依赖新鲜地址。射频竞争用「建连串行闸门 + 传输窗口」治理，而不是停扫描。
建连串行、传输并行同时建连会让 BLE 栈不稳定、批量反而变慢；连上之后各设备各发各的，互不等待。
命令结果恰好回调一次成功、失败、取消、删除、超时、拒收都从同一个终态收口，用原子完成标记挡住重复回调，业务不用自己防「回调两次」。
协议按运行时注册公开仓库以源码模块编译期依赖 + 运行时 ProtocolRegistry.register 装配；插件声明可配项但不赋值，取值权留给上层。
大数据按「停滞」判超时刷图 / OTA 数据量差异极大，按总时长容易误杀；有进展就续命，停滞才判失败，并配合 WakeLock 与写入窗口保序。
可观测优先任务自带状态、进度、已发/总字节、结果与失败阶段；配置中心可列出全部可配项，便于诊断与生成配置页。
