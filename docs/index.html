03

发一条命令

三步：拿任务、发命令、收结果。

// 1. 拿任务：一台设备一个任务
QTask task = QingzhuSdk.getTask(mac);
// 没有才创建；反复进出页面请直接用 createTask，见架构图 07
if (task == null) task = QingzhuSdk.createTask(mac);

// 2. 发命令：每条命令恰好回调一次
task.send(
    QCommand.builder().send("{\"action\":\"echo\"}").build(),
    result -> {
        if (result.isSuccess()) {
            String payload = result.payload();
        } else {
            TaskStage stage = result.stage();
            String error = result.error();
        }
    }
);
判断成功只看 isSuccess()。payload 是设备回显，成功也可能为空，不要用 payload 判成败。

完整接入步骤见 README 的「接入文档」一节

05

已知边界

send 不是线程安全的。MQTT 等子线程并发调用要自己串行化，否则可能出现两条命令同时发。
任务不会自动回收。长期运行的服务需要定时 deleteTask，否则任务池只增不减。
没有设备主动上报通路。QTask 没有 listen，设备主动推送的数据暂时收不到。
只有 Android 实现。BleAdapter 是平台抽象，但只有一份实现。

02

两个队列，别混在一起

任务池是集合，不是队列；真正的队列在任务内部。

任务池 QTaskPool

装设备。无序，各自推进，互不等待。

设备 ASENDING
设备 BQUEUED
设备 CREADY
设备 DSEARCHING

指令队列 PendingIntentQueue

装命令。先进先出，同一设备严格串行。

命令 1执行中
命令 2等待
命令 3等待
…默认上限 10000
关键：一个任务里可以有 10000 条命令，但一台设备同一时刻只发一条。跨任务才可能并发（受 7 条连接和传输窗口限制）。

任务之间并行推进，任务内部串行执行

03

任务状态机

状态是任务自己的，另一台设备有另一条轨迹。

UNKNOWN只有 mac
READY有设备未连
QUEUED等窗口/重试
CONNECTING建连中
CONNECTED已连接
SENDING发数据
连接失败 / 发送失败 / 寻人超时→ QUEUED，1.5 秒最多重试 3 次

没有 FAILED 状态，失败后回到 READY 或 UNKNOWN；失败阶段看 TaskStage

04

一条指令进来，只有四种去向

前三件事都是确定的，只有最后一种会丢指令。

任务当前状态新指令的结局是否丢
已被删除立即回调 CLOSED丢
空闲立即执行，状态往前推不丢
忙碌进指令队列，等前一条完成不丢
队列已满立即回调 BUSY丢
队列上限已从 8 调到 10000。正常业务下 BUSY 几乎不会再出现，剩下唯一会丢的情况是任务已被删除。

队列只影响等待，不影响顺序

1连接
1指令队列

06

场景二：批量配置

N 台就是 N 个任务，一台失败不影响其他。

01
去重按 MAC 转大写去重，total 用它算
02
循环 send每台 getTask，没有才 createTask
03
连接池排队7 条并发，其余进无界队列等槽位
04
逐个回调主线程，计数 done == total
05
全部结束汇总成功与失败，再退出
必须先去重。重复项会让同一台设备被配多次或任务被反复替换，且 total 与回调次数对不上。

100 台约等于 100 除以 7，再乘单台耗时

07

重复设备，与反复重进页面

两件事结论相反：重复项要合并，重进页面要换新任务。

重复 MAC：用 getTask

同一个任务，指令进队列，全部执行。

命令 1执行中
命令 2排队
命令 3排队

重复 MAC：用 createTask

每次换任务，前面被删，只留最后一条。

任务 1已删
任务 2已删
任务 3执行中
重进页面是例外，必须用 createTask。Android 销毁页面可能晚于新页面启动。旧页面清理的是自己那个 taskId，新任务 id 不同，才不会被误删。用 getTask 复用，旧页面一清理就断了新页面的连接。
配套写法：清理时带 taskId，只删 id 匹配的那个。

同一页面内连续配置用 getTask，反复进出页面用 createTask

08

场景四：网关持续下发

MQTT 随时来指令，一个任务不断接。

01
MQTT 到达子线程，不能直接调 send
02
投递到主线程保证 send 串行，避免两条指令同时发
03
getTask / createTask设备已有任务就复用
04
send进队列或立即执行，回调上报结果
05
定时回收空闲任务 deleteTask，防止只增不减
代码现状：execute 内部没有锁。并发调用 send 可能都读到空闲，导致两条指令同时发、回包串在一起。必须由调用方串行化（统一投递主线程）。
任务不会自动回收。每台设备建过的任务会一直留在池里，每次状态变化都要遍历全部任务生成快照，越跑越慢。

队列已够大，串行化和回收要自己保证

09

取消与删除

cancel 是停，delete 是换。不是同一个对象的两档冷热。

维度canceldelete
任务对象保留，id 不变移除，下次是新 id
已发现的设备保留随任务一起丢
链路回到操作开始前一定断开
未完成指令回调 CANCEL回调 DELETE
观察者仍然有效一并清空
下次再发直接 send先 createTask
两个细节：cancel 对空闲任务直接返回，什么都不做；delete 不挑状态，空闲也删，连着也会断开。

差在寻人和建连：cancel 保留设备信息，delete 只剩一个 MAC

10

数字与边界

7并发连接
1传输窗口
10000每设备指令队列
∞连接等待队列
3失败重试
边界状态说明
send 线程安全需调用方保证内部无锁，并发调用可能串包
任务自动回收未提供需定时 deleteTask
状态通知开销O(n)每次变化生成全量快照，上千任务会卡
排队超时无连接队列里的请求要等前面全部完成
设备主动上报未实现QTask 没有 listen
非 Android 平台仅设计BleAdapter 是抽象接口，只有一份实现

数字来自当前源码：QTaskPool 与 ConnectionPool 的默认值

01

QingzhuSdk 门面

静态方法，进程内单例。重复初始化幂等。

方法作用
init(Context)初始化内核与适配器，注册 Eddystone 与 Generic 两个开源协议
registerProtocol(ProtocolPlugin)注册协议插件，重复注册同一 id 幂等；注册后立即触发 install()
getProtocols()当前已装配的协议 id 列表
startScan(ScanListener)开始扫描，默认参数
startScan(ScanOptions, ScanListener)带过滤条件的扫描
stopScan() / restartScan()停止 / 重启扫描
setScanStateListener(ScanStateListener)监听扫描开关状态
createTask(String mac)新建任务。会先删除该设备已有任务
createTask(QDevice)用扫描到的设备建任务，同样先删后建
getTask(String mac)只查询，没有返回 null
deleteTask(String mac)取消、断开、从任务池移除
observeAll(Object owner, TaskListListener)观察全部任务，注册后立即推一次全量快照
snapshots()当前所有任务的不可变快照列表
setMaxConnections(int)并发连接数。0 = 用体检建议值，1-N = 手动固定
setMaxTransfers(int)传输窗口。1 = 串行，N = 最多 N 台同时发
setMaxRetries(int)失败重试次数，默认 3
setMaxPendingIntents(int)每设备指令队列上限，默认 10000；0 = 忙碌时直接失败
setConnectCallbackTimeoutMs(long)系统连接回调兜底，默认 20 秒
getConcurrency()当前生效的并发容量
settings()全局设置中心，含协议声明的可配置项
02

QTask 任务

一台设备一个任务。所有读写方法都可随时调用。

方法说明
send(QCommand, TaskCallback)发命令。被接收就恰好回调一次；队列满回调 BUSY
connect(TaskCallback)连接并保持。已连接时立即回调成功
disconnect()真正断开，任务保留
setConnectParams(Map)设置连接参数，对该任务之后的所有连接生效
observe(Object, TaskObserver)观察本任务，回调不可变快照
cancel()中止当前操作，回到操作开始前的链路状态，任务保留
delete()取消 + 断开 + 从任务池移除
id()任务 id。清理时用它判断是不是自己那个任务
deviceMac() / currentMac()任务绑定的 MAC / 当前实际连接的地址
getDevice()扫描解析出的设备，未找到时为 null
getState()当前状态，见枚举
getOutcome()最近一次命令的终态分类
getResult()设备回执，可能为 null
getError()最近一次失败原因
getProgress() / getSentBytes() / getTotalBytes()发送进度与字节数
pendingIntentCount()待办队列里还有几条
isDeleted()是否已被删除
反复进出页面时用 createTask。旧页面的销毁可能晚于新页面启动，用同一个任务会互相干扰。清理时带 taskId 只删自己那个。
03

QCommand 命令

用 Builder 构造。keepConnected() 与 disconnectAfter() 互斥。

方法说明
connect()只连接，不发送
send(String json)发文本 JSON
send(String json, byte[] data)JSON + 单块字节
send(String json, Map attachments)JSON + 多附件，大块数据走这里
keepConnected()发完保持连接
disconnectAfter()发完明确断开，优先于任务的保持期望
noAck()标记无需应答。目前只是标记，未传给底层
reconnect(ReconnectPolicy)意外断开后的重连策略，默认关闭
build()两个互斥项同时出现时抛 IllegalStateException
发完断不断的判断：命令没有声明 disconnectAfter，且任务上有保持期望或命令声明了 keepConnected 时，保持连接。
04

TaskResult 命令结果

每条被接收的命令回调一次。

方法说明
isSuccess()判断成功的唯一依据
payload()设备回执，成功也可能为 null
error()失败原因
stage()失败发生在哪一步，见 TaskStage
